# CRM Module Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Turn the existing CRM backend skeleton (Deal + Activity, already wired) into a production CRM vertical — sales pipeline, activity timeline, partner 360, and a full frontend — consistent with the rest of POS-CAFE.

**Architecture:** NestJS module under `apps/api/src/modules/crm/`, tenancy-scoped via the existing Prisma extension + `TenantContextService`. CRM is built on `Partner` (no new partner tables) with `Deal` + `Activity` as the two CRM tables, plus an `OpportunityStage`-style config later. Frontend is React (Vite) under `apps/web/`, following the InventoryDetailPage pattern.

**Tech Stack:** NestJS 10, Prisma (PostgreSQL 18), React 18 + Vite + React Query, Tailwind, class-validator DTOs, Swagger, existing kernel (audit, events, sequences, permissions, module registry).

## 1. Approach

Three phases, each ending in a green build (`npx tsc --skipLibCheck` + `pnpm lint:arch`) and a commit:

- **Phase A — Backend hardening** (schema tweaks + service/controller upgrades, no new tables unless needed)
- **Phase B — Frontend** (API client, Deals pipeline, Deal detail, CRM dashboard, Partner 360 tab)
- **Phase C — Integrations + polish** (POS customer 360, invoice/deal link, permissions, nav, tests, E2E)

Conventions to respect everywhere (from memory + codebase):

- Tenancy: always `organizationId` from `this.tenant.organizationId`; use `prisma.client` (extension applies soft-delete + tenancy) and `prisma.raw` when explicit scoping is needed. Never a `findUnique({ where: { id } })` without org check.
- Soft delete: `deletedAt` on every business table; service layer provides `delete → soft`, `restore`, `listDeleted` (mirror MenuItem pattern: `DELETE /hard`, `PATCH /restore`, `GET /deleted`).
- Audit every mutation via `AuditService.record`.
- Publish domain events via `EventBus` for anything another module may care about.
- UI: InventoryDetailPage pattern — breadcrumb → header bar (icon + badge + code) → gradient tab bar → card content with `bg-muted/30 border-b rounded-t-lg` headers; `InfoRow` (dl/dt/dd, uppercase text-xs) for key-value; filter controls on lists; React Query for data; DTOs validated in frontend with Zod-style or manual guards matching the API DTOs.
- Module registry: every new permission key must be registered in `crm.module.ts` `onModuleInit`.

**Step 1 — Service changes:**

```ts
// removeDeal → soft delete (sets deletedAt), keep the won-deal guard
async removeDeal(id: string) {
  const deal = await this.requireDeal(id);
  if (deal.stage === 'won') throw new BadRequestException('Cannot delete a won deal; archive it instead');
  const updated = await this.prisma.client.deal.update({ where: { id }, data: { deletedAt: new Date() } });
  await this.audit.record({ entity: 'Deal', entityId: id, action: 'delete', newValues: { deletedAt: updated.deletedAt } });
  this.events.publish('crm.deal.deleted' as any, { organizationId: this.tenant.organizationId, dealId: id });
  return { ok: true };
}

async restoreDeal(id: string) { /* clear deletedAt + audit */ }
async listDeletedDeals() { /* where deletedAt != null, include partner */ }
// removeActivity → soft delete; restoreActivity; listDeletedActivities
```

**Step 2 — Controller routes:**

```ts
@Delete(':id')                    // soft delete
@Patch(':id/restore')             // restore
@Get('deleted')                   // list deleted (place BEFORE @Get(':id'))
```

## Risks / tradeoffs / open questions

- **Tenancy extension trap (highest risk):** if `deal`/`activity` aren't in the tenancy.extension model list, soft-delete filters silently won't apply. Verify FIRST (Task A1 Step 3).
- **Permission split:** introducing `crm:*` keys requires the permission catalog + role seeding to be updated; existing roles won't have them until seeded. Decide: seed into the admin role by default, or keep `partner:*` fallback. (Default recommendation: seed `crm:*` into admin + document.)
- **Analytics cost:** groupBy over 6 stages is cheap; top-customers + partner 360 need joins on `Document`/`Payment` — verify index on `Document.partnerId` exists (Partner relation suggests yes) and add `@@index([organizationId, partnerId])` if missing.
- **Deal↔invoice link** depends on whether invoicing publishes `invoice.created` events — check `EventBus` usage in `invoicing/` before building the subscription. If absent, ship manual link only.
- **Scope guard:** the user's ask is "add CRM" — the skeleton already covers deals+activities. Don't over-build (no campaigns, no email sync, no lead scoring in v1). YAGNI.
- **Currency:** schema defaults to `USD` but the system is IDR — make the frontend default to the org currency (check `Currency`/`Setting` for org default) and format amounts with existing IDR formatter.
